# Separating release changes from model and operator differences

The G6, Vodafone ONT and Beacon 9 are clearly members of a shared Nokia software
lineage. The common configuration model, security-engine formats, password
material and startup scripts give us more than similar product names to go on.
It makes sense to investigate a difference in their shared management software
as a release or build-policy change before calling it unique to Beacon 9.

That is the working hypothesis recorded here. The stronger statement that every
non-hardware difference is a 25.xx change does not yet fit all the evidence.
The ONT is especially useful because it has two 24.03 maintenance builds,
including one built in September 2025. It places some mechanisms previously
seen only on Beacon 9 into the earlier release family.

## Builds examined for account creation

The later ONT-B capture adds JJL.K24p02, built in November 2024 on R24.03. Its stock `sec_extfs` helper and phase dispatcher match the two later ONT builds. K24 account creation remains outside the tests in this comparison. [ONT-B findings](../xs2426xa-24-03-comparison/README.md#a-second-ont-preserved-an-earlier-r2403-build).

| Captured product/build | HomeOS | Operator sample | Normal dedicated ONTUSER creator |
| --- | --- | --- | --- |
| G6 IJL.J03p01 | 24.02.00 | BOQA | Implemented; examined offline |
| XS-2426X-A JJL.K67p02 | 24.03.01 | Vodafone VDQA | Implemented; recovered cfgmgr path |
| XS-2426X-A KJL.K50p01 | 24.03.01 | Vodafone VDQA | Implemented; recovered cfgmgr path |
| G6 HJL.L91p01 | 24.04.00 | BOQA | Implemented; live current-generator match also supplied |
| Beacon 9 JJM.K44p01 | 25.03.00 | BOQA | Normal callers reach a 64-byte no-op |
| G6 25.03 or later | Not captured | Not measured | Unresolved; documentary guide is not a binary |

The G6 and ONT creators initially create the account, then consider
`DebugRnPassEnable` for the factory `EXT_DBG_PWD` override. That flag is not the
initial-creation switch. Both ONT image IDs select the same `JLK` version slice
in the traced deprecated-index2 path. On Beacon 9, the ordinary creator at
`0x6d200` is inactive even though related generators, schema and generic account
routines remain. Its cleanup routine preserves the ONTUSER name when scanning
existing databases. This does not establish a release-wide action which deletes
all pre-existing ONTUSER accounts during an upgrade.

## Which differences can be attributed to a release?

| Mechanism or observation | What the samples establish | Current interpretation |
| --- | --- | --- |
| Ordinary ONTUSER creation | Works in G6 24.02/24.04 and ONT 24.03; inactive in Beacon 9 25.03 | Strong candidate for a later release/build-policy change; not yet isolated from model/SDK policy |
| `sec_extfs` source5 helper | Present in ONT 24.03 and Beacon 9 25.03; missing in examined G6 images | Already exists before 25.xx; not a new 25.xx mechanism |
| Phase-script dispatcher | Shared by ONT 24.03, G6 24.04 and Beacon 9 25.03 | Shared earlier lineage; not unique to Beacon 9 or introduced universally in 25.xx |
| `key0/1/2/7/12/13/14/17` | Equal in all five packaged stores | Shared constants across these builds; no evidence that 25.xx introduced them |
| Deprecated ONTUSER index2 and Password2 public key | Same selected generator material and same ECC verification file across all five | Shared machinery; caller behavior and runtime challenges still matter |
| `key3` and `key4` | Change within both the G6 pair and the ONT 24.03 pair | Can change between maintenance builds without a new major train |
| `key7_2` | Stable within the G6 pair and ONT pair; G6, ONT and Beacon 9 profiles differ | Profile difference; model/operator/build contribution not isolated |
| Factory credentials, service keys, `EXT_KEY_FW` | Per-unit and optional-field differences; Beacon 9 has wrapped firmware material absent from the five other factory records | Provisioning is a separate axis; no universal 25.xx provisioning rule established |
| VDQA WebUI/password and Wi-Fi rules | ONT operator sections differ from BOQA; VDQA defaults also change between its two 24.03 builds | Operator recipe and maintenance changes, not a hardware-only or major-release-only explanation |
| Package versions and component changes | Differ between trains and within 24.03 | Must compare exact builds; a train label alone is insufficient |

For source5 specifically, the ONT and Beacon 9 `secInit` files are byte-identical.
Their helper concatenates accepted decoded factory strings in a fixed order and
hashes them. Actual databases now decode using each unit's own source5. The G6
missing-source fallback remains correct for all four examined G6s. This is a
concrete counterexample to dating every Beacon 9 software mechanism to 25.xx.

The ONT maintenance pair provides another useful control. Its packaged security
engine, helper, public Password2 key and ONTUSER mechanism remain, while
preconfiguration, schema, management packages and operator defaults change.
`key3/4` rotate but `key7_2` does not. Thus a software change need not mean a new
release train, and an unchanged key does not mean every surrounding path matches.

## What remains confounded

The G6 and ONT are Cortina/glibc targets; Beacon 9 is Qualcomm/musl. Build flags,
SDK integrations and product conditionals can affect common management code as
well as drivers. BOQA versus VDQA adds operator policy, and factory fields add
per-device provisioning. Four G6 units improve confidence in the sampled G6
profiles but do not provide a G6 running 25.xx.

A same-model comparison across 24.xx and 25.xx would isolate the release axis
much better. A G6 25.03+ image with a no-op creator would establish that behavior
for that G6 build. A working creator would disprove a universal 25.xx removal.
Neither outcome alone would prove the rule for all operators and products.
Similarly, a Beacon 9 24.xx image, if one exists and is obtained, would be useful;
its existence is not assumed here.

## Keep documentary releases separate

The dated public index contains a G6 25.03 guide and a Beacon 9 25.03a guide.
Beacon 9's captured buildinfo says 25.03.00, while component notes mention
BBDR2503a. These identify related release families, not an identical complete
firmware image or all point-release changes. The existing advisory evidence
concerns a WebUI validation fix; it does not identify ONTUSER removal as the fix.
No newly acquired G6 25.xx binary or vendor source conditional resolves that gap.

The [captured-build catalogue](README.md), [documentation list](documented-releases.md)
and [new-capture checklist](new-capture-checklist.md) retain the separate evidence
classes. Account presence alone is weaker than tracing the stock creator because
saved state, owner scripts or manual changes can alter the live account database.
The ONT owner reports no modifications; that is recorded without equating its
capture with a factory-fresh device.
