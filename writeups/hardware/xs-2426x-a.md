# Getting to know the Nokia XS-2426X-A

The XS-2426X-A is a fibre ONT built around the same Cortina Venus platform family as the Beacon G6. It adds an optical uplink, telephony and a 10GbE copper interface to a dual-band Wi-Fi design. Sharing a SoC family explains much of the familiar firmware, but does not make the two boards interchangeable.

The project has captures from two XS-2426X-A units, `ONT-A` and `ONT-B`, with three HomeOS 24.03 builds between them. ONT-A was identified by the owner as a Vodafone unit. The evidence includes full NAND main-area captures, recovered kernel/FIT images and original board device trees. It does not include a board teardown, a complete live PCIe/PHY survey or an optical performance test.

The [Nokia product guide, Issue 5](https://device.report/m/3e114996ba0936e00a289ad55208ef25e6a5a75a0b2d54f5180a5b3a4d729b7b) supplies the published component and interface design. Firmware declarations and captured flash sizes corroborate the platform, but not every component marking or populated board option.

## Ports, power and enclosure

The published connection labels distinguish `LAN1`, `LAN2`, `LAN3`, `10GE`, `TEL1` and `TEL2`, alongside USB, power and the optical connection. The optical interface is the service-provider uplink; the 10GbE socket is a separate subscriber-side interface. Their rates describe different links in the path, rather than a measured end-to-end transfer.

The guide lists a **12 V, 3 A** adapter for the described kits. Its diagram connects the faster copper port through an **AQR113C** PHY. Those are design specifications, not readings of the adapter or chip markings on ONT-A/ONT-B. [Published connections and block diagram](https://device.report/m/3e114996ba0936e00a289ad55208ef25e6a5a75a0b2d54f5180a5b3a4d729b7b).

Nokia's June 2025 quick reference gives **226 × 85 × 175 mm**, 1.38 kg, and standby/typical consumption of **11.6/15.4 W**. These are published enclosure and operating figures, not measurements of the captured ONTs. [Quick reference](https://www.nokia.com/asset/f/212658/).

The firmware contains optical, voice and USB support, but the existence of those packages does not establish which services an operator provisioned. An analog phone connector requires the voice circuit and software configuration; a PON connection requires optical registration and compatible service provisioning. Neither follows merely from enabling a generic configuration flag copied from another device.

## Identifying the board in the firmware

The FIT includes `/images/fdt@xs2426xa.dtb`, selected through the corresponding `conf@xs2426xa.dtb` configuration. Its root model is `Cortina Access Venus REF Board`, with compatibles `cortina,venus` and `cortina,ca8289`. The reference-board name is a generic software label; the product-specific FIT selection is what connects this tree to the ONT image.

All three captured 24.03 versions contain the same **38,932-byte DTB**, SHA256:

```text
bcc45bcbac6e405fec749ef33b29a79bbb6683ac11053777b6246d8eb6f7b666
```

That establishes one common packaged board description across `JJL.K24p02`, `JJL.K67p02` and `KJL.K50p01`. It does not establish byte-identical kernels or complete boards: the kernel payloads differ, and the DTB does not record every possible component substitution.

The CPU nodes describe Cortex-A55 cores at affinity values `0x000`, `0x100`, `0x200` and `0x300`. Their startup uses PSCI with secure-monitor calls. This is stronger evidence than an `aarch64_cortex-a53` package label, which describes the compiler target. A live core/frequency survey would still be needed to report actual clock settings on these ONTs.

## RAM: distinguish the design from the packaged memory property

The published DDR organization implies a gigabyte-class design, while the unmodified packaged tree's `/memory/reg` describes only **240 MiB** starting at address zero. This is the same kind of limitation encountered in the G6's packaged tree. It is not evidence that the ONT physically contains only 240 MiB of RAM.

A bootloader can adjust memory properties, and the running kernel also excludes regions reserved for hardware or firmware. The project has not captured the final runtime memory property or `MemTotal` for either ONT. The appropriate description is therefore a published memory design plus a smaller packaged declaration, rather than an invented live total.

The shared Cortina board description includes reservations for Taroko processing engines, wireless firmware, PCIe radio buffers, DMA pools and crash logging. These regions explain why a working Linux system can report less usable RAM than the physical device capacity. They are not additional memory chips, and a kernel-reported usable total should not have the same reservations subtracted from it again.

Boot-time carve-outs can reduce `MemTotal`. Ordinary driver allocations from memory already managed by Linux instead consume free/available memory without changing that total.

The NAND label in the product-guide diagram introduces another unit problem: it says “4GB”, whereas the captured main-area partition layout totals **512 MiB**. A 4-Gbit device would correspond to that capacity, but the publication's lettering must not silently be rewritten as a measured 4-Gbit part. Here the dump establishes the examined layout; the label remains a documentation discrepancy.

## Ethernet and the optical path

The faster copper interface adds a PHY and board wiring that the G6's 2.5GbE paths do not share. A common CA8289 driver family is therefore only part of the hardware match. PHY firmware, MDIO address selection, interface mode, reset timing and the connector-to-port map can differ even when the high-level Linux API looks familiar.

The optical side adds the PON MAC/BOSA path and its own provisioning and management behavior. OMCI software in the image is consistent with an ONT, but the saved rootfs does not provide measurements of optical power, registration state, GEM/T-CONT assignment or line throughput. An optical line-rate specification is not an application-speed result.

The available captures also do not establish which Linux interface or Cortina port number corresponds to the printed `10GE` label. The G6 research already shows why that matters: link negotiation, VLAN admission, CPU trapping and bridge membership are separate questions. Reusing a G6 port number without a mapping would bypass the board-specific part of the problem.

For an independent OS, the optical path is an additional dependency beyond ordinary Ethernet forwarding. Preserving the existing calibration and provisioning regions is separate from reconstructing a usable Linux network configuration. [Cortina hardware controls](../cortina-hardware-controls/README.md) · [Uplink and VLAN ownership](../uplink-vlan-firewall/README.md).

## Wi-Fi and its supporting processors

The board tree enables two two-lane PCIe controllers, at `0xf4325000` and `0xf4326000`. A third controller at `0xf4327000` is disabled. These are controller declarations, not a fresh PCI enumeration showing installed radio IDs or negotiated link width. The generic Qualcomm radio/firmware family names in the filesystem should not be treated as a chip-marking photograph.

The three 24.03 builds retain the same board DTB and Wi-Fi-offload image, while later firmware files add board-data entries. That is a packaging difference; it does not establish which calibration entry a running radio selected. Radio startup requires the matched firmware, board data, reserved memory and vendor driver path.

The normal early Linux startup loads `/taroko/wfo-qca-nss-pe0.bin`. It is the same **403,724-byte** Zephyr Wi-Fi-offload payload present in the captured G6 24.02/24.04 images, identifying `zephyr-v1.13.0-155-g89629ff620`. This is an exact file comparison, not merely a shared filename.

Other packaged Taroko applications cover IPsec, MAP-T and throughput testing. Their presence is not evidence that those optional applications ran on either ONT. The G6's preserved UART log confirms a WFO Zephyr boot there; no equivalent ONT packet-engine boot was observed in this hardware comparison. [Zephyr packet-engine evidence](../../knowledgebases/zephyr-packet-engines.md).

## NAND, firmware banks and device-specific regions

The supplied full NAND main-area layout has twelve named physical partitions: `ssb`, `uboot-env`, `RI`, `rootfs0`, `rootfs1`, `rootfs_data0`, `rootfs_data1`, `cfg`, `log`, `extfs`, `0:ART` and `user_data`. The two firmware banks are **80 MiB each**. Their UBI volumes separate the FIT, root filesystem and Wi-Fi firmware.

The partition names and sizes match the examined G6 layout, but this is not permission to substitute complete images between products. The ONT has its own board selection, optical requirements, factory material and mutable settings. Equal partition boundaries say nothing about whether another model's radio or boot configuration is compatible.

The acquired `.bin` files contain main-area bytes. The reported 256-byte OOB geometry does not mean those bytes were included in the files. Page/OOB/ECC handling therefore remains important for any low-level restore plan. A complete main-area backup and a raw page-plus-OOB acquisition are different artifacts.

In the ONT-A snapshot, `rootfs1` was the active firmware bank and `rootfs_data1` the selected writable store. That is an observed state, not a universal factory default. The second capture adds an older alternate image. [ONT capture comparison](../xs2426xa-24-03-comparison/README.md) · [Storage and flash](../storage-and-flash/README.md).

## Serial, USB, GPIO and the watchdog

The original tree describes several familiar Cortina resources:

| Resource | Packaged board address |
| --- | --- |
| UART0 | `0xf4329188`, span `0x30` |
| UART1 | `0xf43291b8`, span `0x30` |
| Watchdog | `0xf432901c`, with a separate reset-control resource |
| GPIO controller | `0xf43292c0`; mux resource at `0xf4320080` |
| MDIO controller | `0xf4329118` |
| USB 3 xHCI | `0xf0200000`, span `0x80000` |
| USB 2 xHCI | `0xf0400000`, span `0x80000` |

Unlike the G6's unpublished physical USB access, this ONT's published design has an external USB interface. The controller declarations support that inventory, but a USB device was not plugged in as part of this investigation. Sharing a USB PHY node with another product does not establish identical power switching or connector wiring.

The product documentation identifies UART/JTAG headers in its block diagram. Their existence in a diagram does not supply pad positions, signal voltage or proof that a debugger is unlocked. The available shell access is also not a verified UART recovery procedure. No electrical pinout is claimed here.

The watchdog and GPIO addresses are useful starting points for a port, but no GPIO was driven and no watchdog was stopped on an ONT during this comparison. A G6 recovery sequence cannot be declared tested on this model simply because the controller names match.

## What changed across the captured ONTs?

The three versions share the same original DTB and WFO payload. The captures therefore expand the software chronology without showing a changed CPU/radio board design. Device-specific configuration, factory credentials and boot metadata remain separate; matching software does not make those values interchangeable.

The remaining hardware work is concrete: final runtime RAM/clock reporting, PCIe and MDIO enumeration, physical chip markings, connector-to-port mapping, UART/JTAG electrical identification and an optical-path bring-up record. These gaps do not erase the platform, flash and board-description evidence already available.

The [full ONT board properties](resources/ont-board-evidence.json) and [XS-2426X-A hardware knowledgebase](../../knowledgebases/hardware-xs2426x-a.md) retain the original node bytes, hashes, publication discrepancies and acquisition limits. The article's hardware claims do not depend on publishing any ONT serial number or factory secret.
