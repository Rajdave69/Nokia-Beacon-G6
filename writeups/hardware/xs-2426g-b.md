# Getting to know the Nokia XS-2426G-B

The XS-2426G-B places an optical uplink, Ethernet, Wi-Fi and telephony around Cortina's Venus platform. It is particularly useful to this project because its recovered R21/R23 firmware preserves earlier versions of components still found on the Beacon G6 and XS-2426X-A.

The available sources have different strengths. Nokia's product guide describes a board design. Three recovered firmware-bank images provide original device trees, drivers and auxiliary firmware. There is no full NAND/factory capture or live hardware survey for these particular source units. The collection describes the images as sanitized; that is a source description, not an independent certification that every device-specific field was removed.

These published component names come from Nokia's [December 2021 product guide](https://fccid.io/m/1d1e863108baa7100cb40a6032cd7fded60bf40fc5533f8a91e869b539a7d8f6.pdf). They describe that documented design; they are not independently read chip markings from the source units.

## Ports, controls and power

The guide's ordering description specifies **3×GE + 1×2.5GE**, two POTS connections and USB, with a **12 V, 3 A** adapter for the listed kits. The optical connection supplies the provider-facing uplink. This makes the port roles different from an Ethernet-WAN Beacon even where the same SoC and radio family are involved. [Published interface design](https://fccid.io/m/1d1e863108baa7100cb40a6032cd7fded60bf40fc5533f8a91e869b539a7d8f6.pdf).

The copper PHY's supported rate is only one part of a working link. The SoC interface mode, MDIO setup, VLAN rules and forwarding configuration still have to agree. None of the recovered bank files supplies a cable-to-port experiment that maps the physical connectors to Linux or Cortina SDK identifiers.

The physical dimensions are not consistent across Nokia publications. The older guide gives **225 × 85 × 160 mm**; the [June 2025 quick reference](https://www.nokia.com/asset/f/212398/) gives **226 × 85 × 68.8 mm**. Without measuring a unit or establishing document-specific hardware variants, that discrepancy should remain a publication disagreement rather than evidence of a smaller board revision.

## Which firmware and board descriptions were recovered?

| Numeric version | Product image ID | Software version | Build date |
| --- | --- | --- | --- |
| `1.2104.612` | `3FE49544JJIL12` | `JJI.L12p01` | 2022-01-16 |
| `1.2303.402` | `3FE49544IJKK02` | `IJK.K02p03` | 2023-09-27 |
| `1.2303.544` | `3FE49544JJKK44` | `JJK.K44p03` | 2024-07-02 |

Each FIT contains `/images/fdt@xs2426gb.dtb`. The R21 image's DTB is **38,210 bytes**. Both R23 images contain the same **38,868-byte** DTB, so the later R23 maintenance build did not change that packaged board description.

All three describe `cortina,venus` and `cortina,ca8289`, with the generic model `Cortina Access Venus REF Board`. Four CPU nodes identify `arm,cortex-a55`, with affinity values `0x000`, `0x100`, `0x200` and `0x300`. PSCI uses secure-monitor calls for CPU startup.

This ties the images to a concrete platform more reliably than a generic package architecture string. It still leaves actual clock settings and live device enumeration unmeasured. A firmware description can include disabled or unpopulated reference-board options, and the source units' boards were not opened.

The R21/R23 family labels come from the supplied numeric versions and build evidence. They should not be relabelled as G6 HomeOS 24.xx images, nor should their build dates be treated as the manufacturing dates of the hardware. [Older firmware comparison](../xs2426gb-21-23-comparison/README.md).

## RAM: three different quantities to keep separate

The published memory values conflict within the older product guide: its narrative lists **512 MB RAM and 256 MB NAND**, while the block diagram shows **1024 MB DDR3 and 512 MB flash**. That conflict could reflect documentation or product-option differences; the captured banks do not resolve the physical population of the source units.

The original `/memory/reg` in all three packaged DTBs describes **240 MiB** at address zero. That is a third quantity, not a measurement proving either published memory arrangement. The G6 investigation demonstrates why: a bootloader can expand the final memory declaration beyond the template stored in the FIT.

Linux then has another constraint. Reserved areas for hardware buffers, radio firmware, auxiliary processing and secure-world services reduce the memory available to its allocator. A `MemTotal` figure would therefore be useful runtime evidence, but would not be a substitute for physical capacity. No such live snapshot was supplied for the XS-2426G-B source units.

The ONT trees include the familiar Cortina reserved-memory structure. The Taroko regions represent memory used by separate packet engines; wireless and DMA reservations support communication with radios and the datapath. These regions are not additional physical memory devices. They also cannot simply be added to or subtracted from an already reduced Linux total without checking the final running map.

Boot-time carve-outs can reduce `MemTotal`. Ordinary driver allocations from memory already managed by Linux instead consume free/available memory without changing that total.

An 80 MiB firmware bank does not establish a 512 MiB flash chip. It establishes the bank's logical extent. Without the whole-device partition map, acquisition geometry and chip identification, a flash-capacity claim must remain attached to the publication that supplied it.

## The optical, Ethernet and voice paths

The design combines the CA8289's packet-processing platform with an optical front end and separate subscriber interfaces. Its published RTL8221B path gives the faster copper interface a different external PHY from the XS-2426X-A's 10GbE design. That is a hardware difference despite the common software family.

The firmware includes optical-management and voice components, consistent with its ONT role. Their presence does not establish an active provider service, successful optical registration or working analog telephony on the source units. The POTS circuit, optical hardware, calibration and provider provisioning are dependencies outside a generic WebUI switch.

For the same reason, converting a stock configuration to a bridged mode cannot create an optical front end on a Beacon G6. Conversely, an ONT port configuration cannot be transplanted to the G6 merely because both use Cortina interface names. The shared management model is broader than the physical board inventory.

The recoveries provide no negotiated Ethernet-rate snapshot, complete MDIO list or optical-power reading for this model. An independent port would need those board-specific checks in addition to the software and register catalogues already developed for the G6.

## Wi-Fi and PCIe

The published design uses two QCN9024 radio devices. Independently, the original DTBs enable two PCIe controllers with **two lanes each**, at `0xf4325000` and `0xf4326000`, and disable the third controller at `0xf4327000`. The dual-radio design is therefore consistent with the software description, while the actual PCI IDs and negotiated links remain unmeasured on these units.

A controller's lane count does not establish a populated expansion socket, and a disabled third node does not imply a hidden third radio. The Qualcomm wireless paths in the filesystem similarly identify a software family, not the main processor: the host platform remains Cortina CA8289.

Wi-Fi operation also requires matching firmware, calibration data, memory reservations and host/packet-engine integration. Those dependencies are why a radio-capability list alone is insufficient for an independent kernel. The captured images establish the pieces supplied by the firmware without demonstrating a fresh radio bring-up.

## Zephyr on the packet engine

These older images make the auxiliary OS explicit. Their normal early Linux boot script loads `/taroko/wfo-qca-nss-pe0.bin` through the Cortina `rboot` loader. The R21 payload reports `zephyr-v1.13.0-146-ga61ec8a626`; both R23 payloads report `zephyr-v1.13.0-153-gce8f5224aa`.

The WFO images grow from **346,348 bytes** to **396,012 bytes**. The two R23 files match byte-for-byte. Newer captured G6/XS-2426X-A images carry a later 403,724-byte revision. This provides a component-level history independent of the main Linux release number.

The files named `ipsec_dp0.bin`, `mapt_dp0.bin` and `tput_test_iperf3.bin` contain separate Zephyr 1.9-based applications. Their bytes are unchanged across these old images and the newer Cortina captures. The multicast payloads identify themselves as Taroko applications, but their OS has not been assigned from that evidence.

These are auxiliary processor images, not Linux packages. No packet-engine executable was run for this XS-2426G-B comparison. The G6's actual UART boot witness corroborates the newer WFO application on that router; it must not be turned into an observation of these older ONTs. [Complete packet-engine record](../../knowledgebases/zephyr-packet-engines.md).

## Storage: what the supplied bank files contain

Each source bank is **83,886,080 bytes** after decompression. Its UBI layout separates volume 0 `fit`, volume 1 `rootfs` and volume 3 `wifi_fw`. The FIT contains the kernel and board data, the SquashFS volume contains Linux userspace, and the Wi-Fi volume supplies another firmware dependency.

Those bank images omit the source unit's complete bootloader, environment, RI, factory security and writable configuration history. They cannot establish the active slot on a live unit, its stored passwords, its exact NAND chip or whether the installed boot chain accepts an independently built image.

The original root filesystem was recovered offline. A compatibility change was applied only to disposable extraction copies to make the vendor SquashFS readable by the workstation's tool. That did not modify the firmware-bank originals or establish a usable reflash image.

The early R21 startup also attempts to commit the running image after a delay; R23 disables that particular startup commit. This is bank-management software behavior, not evidence of a different flash chip. [Firmware-bank and software comparison](../xs2426gb-21-23-comparison/README.md).

## Serial, GPIO, USB and reset controls

The recovered trees describe the same controller family as the other Cortina devices:

| Resource | Packaged board address |
| --- | --- |
| UART0 / UART1 | `0xf4329188` / `0xf43291b8` |
| Watchdog | `0xf432901c` |
| GPIO controller / mux | `0xf43292c0` / `0xf4320080` |
| MDIO controller | `0xf4329118` |
| USB 3 / USB 2 xHCI | `0xf0200000` / `0xf0400000` |

The original product diagram names UART and JTAG connections, and the published interface inventory includes external USB. The exact debug pads, signal voltage, controller-to-header routing and debug authorization are not established by those declarations. No GPIO, reset or watchdog operation was executed on an XS-2426G-B during this investigation.

This is especially important when using the G6 work as a starting point. Matching MMIO addresses do not establish matching enclosure buttons, LEDs, PHY resets or calibration wiring. Those require the product-specific pin descriptions and physical verification, rather than a copied shell command.

## What this model contributes to the hardware comparison

The strongest shared facts are the CA8289 platform description, four Cortex-A55 CPU nodes, two enabled PCIe radio paths and the evolving Zephyr WFO component. The published optical, PHY and voice design adds the board-specific differences that the shared software cannot supply by itself.

The gaps are also specific: physical RAM/flash population, final runtime memory/clock settings, full NAND geometry, PCIe/MDIO enumeration, a connector map and measured debug wiring. They remain open because the available source is firmware-bank images rather than an inspected and running unit.

The [original ONT board properties](resources/ont-board-evidence.json), [publication provenance](resources/hardware-publications.json) and [complete XS-2426G-B hardware knowledgebase](../../knowledgebases/hardware-xs2426g-b.md) preserve the versions, exact hashes, conflicting specifications and source boundaries without introducing device identifiers.
